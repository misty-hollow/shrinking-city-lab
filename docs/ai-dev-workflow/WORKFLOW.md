# WORKFLOW v1.2

CONSTITUTION.md의 원칙을 실제 작업 순서로 옮긴 것. 프로젝트별 값(검증 명령, 위험 기준, 영향 파일, 모델 별칭)은 그 프로젝트의 CLAUDE.md와 PROJECT_TEMPLATE.md에서 가져온다. 검증·상태·사용자 확인 규칙의 원본은 이 문서 5절이다.

## 1. 사용자가 보내는 메시지

| 메시지 | 언제 |
|---|---|
| 목표 | 작업 시작. 무엇을, 왜, 사용자 관점의 완료 기준. 긴 제품 설명은 정상이다 |
| 제품 질문에 대한 답 | 메인이 방향·범위·UX를 물었을 때 |
| 독립 리뷰 명령 | REPORT.md "다음 할 일"에 적힌 명령 그대로 |
| 사용자 확인 | 다음 할 일에 적힌 항목을 보고, 어느 항목인지 특정되는 말로 ("확인: 보급캠프 화면 정상", "문제: 글자가 겹침" 등 자유 형식) |
| "PR #N 병합해" | 확인이 끝났을 때 |

같은 기술 지시를 작업마다 반복해서 쓰게 되면 그것만 CLAUDE.md로 옮긴다. 일회성 요구는 규칙으로 만들지 않는다.

## 2. 세션 시작

메인은 작업 전에 읽는다: CLAUDE.md 첫 줄이 가리키는 공통 규칙 사본, CLAUDE.md의 프로젝트 값, docs/DECISIONS.md, docs/REPORT.md 상단, `git status`·현재 브랜치·열린 PR. REPORT.md와 git 상태가 다르면 git을 기준으로 삼고 차이를 보고한다. 사본 버전이 원본과 다르면 사본을 따르되 REPORT.md에 적는다.

## 3. 실행 체인

목표를 받으면 멈추는 지점(제품 결정, 독립 리뷰 명령, 승인 대상 행동) 외에는 이어서 진행한다.

1. **조사** — 관련 코드·테스트·결정 기록
2. **설계** — 접근, 영향 범위, 완료 기준. 제품 결정이 필요하면 선택지와 권고안을 들고 질문. 고난도 설계가 필요하다고 판단하면 서브에이전트에 상위 모델을 지정하거나(가능할 때), 메인 전환이 필요하면 "이번 작업은 [모델] 권장"이라고 알리고 사용자의 `/model` 선택을 기다린다
3. **작업 브랜치** — main에서 작업하지 않는다
4. **구현** — 작은 작업은 직접. 분리할 이점이 있을 때만 구현 서브에이전트
5. **로컬 검증** — B절의 검증 중 이번 변경에 해당하는 것을 실행한다. 화면·입력·상태 영향(표시 값·문구·배치·입력 처리·상태 전환 변경, 설정의 영향 파일·영역 해당, 또는 불확실)이 있으면 실행 검증 ①(대표 플레이 경로 + 변경 관련 경로 + 변경 주변 짧은 탐색 + 객관 검사)과 ② 직접 검토를 포함한다. 디버그 핸들·내부 API는 초기 상태 준비와 관찰에만 쓰고, 검증 대상 행동은 실제 입력으로 수행하며 상태와 화면을 함께 본다. 상태 직접 변경이나 내부 함수 호출로 통과한 것은 플레이 경로 수행이 아니다. 배포 형태가 여럿이면 B절이 정한 변경에서 해당 형태로 실제 실행하고, 한 형태의 결과로 다른 형태를 확인했다고 쓰지 않는다. 실패는 4절로. 실패한 입력 순서와 재현 조건은 재실행 가능한 형태로 보존한다
6. **commit과 상태 기록** — 작업 브랜치에 commit하고 REPORT.md 상단을 갱신한다. 이후 의미 있는 단계마다 갱신한다. 첫 commit 전이라도 중단하거나 단계가 바뀌면 상단에 재개 정보(현재 가설, 다음 명령, 미커밋 변경 범위)를 남긴다
7. **리뷰** — 저위험: 필요 시 새 컨텍스트 서브에이전트. 고위험: 리뷰 전 마지막 commit 메시지에 목표·승인된 동작 기준·검증 공백 요약을 넣고, REPORT.md에 `결과: 결정 필요`, `다음 할 일: [독립 리뷰 명령]`을 적고 종료. 독립 리뷰 도구는 로컬 git 상태를 읽으므로 commit만 있으면 된다. 리뷰 결과는 필수/선택으로 나눠 필수만 반영하고 변경 부분을 재검증한다. 두 AI의 판단이 다르면 재현·테스트·근거로 먼저 해결하고 사용자에게 기술 심판을 맡기지 않는다. 리뷰한 커밋 이후 동작·검증·권한·승인 기준이 바뀌면(리뷰 반영, CI 수정, main 반영 포함) 바뀐 부분과 그 영향 범위를 재검토한다. 그런 기준을 바꾸지 않는 기록 수정만 재검토를 생략한다. 고위험 작업당 리뷰 명령 1회는 효율 목표이지 재검토 횟수의 상한이 아니다. 제품 동작이나 승인된 설계가 바뀌는 수정은 사용자에게 결정받는다
8. **push** — 작업 브랜치에 push. 리뷰 전후 어느 쪽이든 된다
9. **PR 생성·갱신과 CI 확인** — PR이 없으면 생성(제목은 변경 요약, 본문에 REPORT.md 상단 3줄과 "검증 공백" 섹션). PR의 최신 변경에 대한 필수 체크를 기다려 확인한다. 실패하면 4절로. 병합 때까지 미루지 않는다
10. **REPORT.md 최종** — 5절 형식. 보고서만 바꾼 push로 PR CI가 다시 돌면 결과는 확인하되 보고서에 반복 기록하지 않는다
11. **종료** — "다음 할 일"에 사용자가 할 것을 적는다: ③ 판단 항목, ②의 불확실 항목, 검증 공백 중 사용자가 눈으로 볼 수 있는 항목, 전환 기간 병행 확인 항목. ①②를 통과한 항목은 전환 기간이 아니면 다시 보라고 하지 않는다

## 4. 실패 처리

작업 예산은 프로젝트 설정의 시간·CI 실행 상한이며, 조사·증거 수집도 예산에 포함된다. 가설이 바뀌어도 예산은 초기화되지 않는다.

| 상황 | 행동 |
|---|---|
| 실패 1회 | 원인 분석 후 수정 |
| 같은 가설로 2회 실패 | 가설 폐기. 로그·재현·범위 축소로 새 증거 확보(이 조사는 실패 횟수에 넣지 않지만 예산에는 든다). 독립 모델 rescue에 "읽기 전용 진단, 코드 수정 금지, 원인·근거·재현·수정 제안만"을 명시해 위임. 읽기 전용 실행을 지원하면 그것을 쓰고, 아니면 가능한 한 별도 worktree 사본에서 진단한다. 호출 전후 `git status --porcelain`·`git stash list`·`git log`(조회 명령)와 미추적 파일 목록을 비교하고, 상태·이력 조회에 더해 `git diff`와 `git diff --cached`의 전후 내용을 비교한다. 기존 미추적 파일이 있으면 해당 파일의 내용 변경(해시 비교)도 확인한다. 이 비교는 변경 탐지이지 쓰기 방지나 저장소 밖 데이터 보호를 보장하지 않는다. 변경이 있으면 보고하고 검토 없이 채택하지 않는다 |
| 새 가설이 없거나, 새 가설로도 진전 없이 예산 소진 | 중단. 결과 `차단됨` 또는 `결정 필요`, 원인 추정·시도·선택지·권고안 기록 |

개별 테스트 실행 횟수는 세지 않는다. 금지: 테스트 약화, 원인 은폐, 임시방편을 완료로 보고.

## 5. REPORT.md 형식과 검증 규칙

```
작업: [한 줄]
결과: 완료 | 검증 대기 | 결정 필요 | 차단됨
다음 할 일: [사용자가 할 일 또는 입력할 명령. 사용자 확인 항목은 "확인 요청 N건" 뒤에 화면·확인 내용 단위로 나열]

## 위험도: 저/고, 근거 한 줄
## 영향: 화면·입력·상태 영향 있음/없음, 근거 한 줄. 전환 기간이면 n/N
## 핵심 변경 / 변경 파일
## 검증 (B절 행마다: 필요 여부 · 수행 상태 · 결과 · 증거)
   수행 상태: 해당 없음 / 수행 / 수단 없음 / 대체 수행(방법) / 선택 미수행 / AI 미수행·사용자 확인(범위, 날짜)
   결과: 통과 / 실패 (수행·대체 수행에만)
## 실행 검증 ①: 실행한 경로, 결과, 보존한 재현 조건
## 직접 검토 ②: 본 결과물, 소견(이상 없음 / 의심→수정 / 확인 불가→검증 공백)
## 검증 공백: 필요하지만 수단 없음 + 선택 미수행. 각 항목에 영향과 해소 방법
## PR CI: PR 번호, 최신 변경 커밋, 필수 체크 결과
## 독립 리뷰: 요약과 조치. 원문은 PR 코멘트
## 사용자 확인 기록: 항목, 확인 범위, 날짜
## 미해결 / commit 해시
```

상태 정의 (이 네 값만 쓴다):
- **완료**: 이번 변경에 필요한 검증이 전부 수행·통과(대체 수행 포함, 또는 아래 조건의 사용자 확인), 필요한 독립 리뷰 통과, PR 최신 변경의 필수 체크 성공. 선택 검증 미수행은 "검증 공백"에 적혀 있음. 사용자 판단(③)과 병합만 남음
- **검증 대기**: PR 필수 체크를 확인하지 못했거나, 필요한 검증에 수단이 없어 수행하지 못함. "다음 할 일"에 수단 확보 작업 또는 사용자가 눈으로 확인할 항목을 적는다
- **결정 필요**: 제품·설계·권한 결정이 필요
- **차단됨**: 환경·접근·외부 의존성으로 진행 불가. 필요한 검증의 실행 실패, 실패 처리 예산 소진도 여기

고위험 리뷰가 끝나지 않은 상태에서는 `완료`를 쓰지 않는다.

**검증의 필요성과 수단** (원본은 여기뿐)
- 검증이 필요한지는 변경의 실패 영향으로 정한다(B절 "필요 조건"). 수단이 있는지는 별개다. 수단이 없다고 필요성이 낮아지지 않는다.
- 수행했다는 것은 통과를 뜻하지 않는다. 실패는 4절로 간다.
- 대체 수행은 수행하지 못한 검증이 잡으려던 문제를 메인이 다른 방법으로 직접 확인한 것만이다. 이미 필요한 테스트·빌드 통과, 코드 읽기, 내부 함수 호출만의 테스트는 플레이 경로·화면 검증의 대체가 아니다.
- 수단 없음 → `검증 대기` → 병합 보류는 필요한 검증에만 적용한다. 선택 검증 미수행은 상태를 바꾸지 않는다. 수단 없음이 있어도 구현·실험·PR 생성은 진행하고, 수단 확보를 다음 작업으로 제안한다.
- 사용자가 대신 볼 수 있는 것은 화면에서 눈으로 관찰 가능한 항목뿐이다. 콘솔 오류·내부 수치·실행하지 않은 테스트·빌드·타입체크는 넘기지 않는다.
- 사용자 확인은 어느 항목인지 특정되는 명확한 말로 한 것만 기록한다. "병합해"만으로는 확인이 아니다. 불명확하면 한 번 되묻는다. 확인된 항목은 검증 공백에서 빼되, 그 검증 행은 "AI 미수행·사용자 확인(범위, 날짜)"으로 남기고 수행·통과로 바꾸지 않는다.
- 필요/선택 지정은 작업 중에 바꾸지 않는다. 변경은 사용자 승인 후 DECISIONS.md.

**보고서 종료 조건**: REPORT.md에는 마지막 코드 변경에 대한 PR 필수 체크 결과까지 기록한다. 보고서만 고친 push의 CI는 확인만 한다. CI에 경로 기반 생략 조건을 두지 않는다.

## 6. 병합

사용자가 "PR #N 병합해"라고 지시했을 때만.

0. REPORT.md 결과가 `완료`인지. 아니면 병합하지 않고 남은 항목을 한 줄로 알린다. `검증 대기`의 원인이 사용자가 눈으로 볼 수 있는 항목뿐이고 사용자가 그 항목을 특정해 확인했으면, 5절대로 기록한 뒤 `완료`로 바꾸고 진행한다. 그 외의 재지시로는 건너뛰지 않는다
1. PR 번호와 base 브랜치
2. PR 최신 변경(head 커밋)의 필수 체크 성공
3. 고위험 변경이 있었으면 독립 리뷰가 최종 변경까지 다뤘고 필수 지적이 반영됐는지
4. up-to-date 조건이 있으면 main을 작업 브랜치에 merge(rebase 아님)로 반영 후 필수 체크 재확인

실행: 일반 merge, 확인한 head 커밋에 고정. 관리자 우회·자동 병합·API 우회 금지.
병합 후 main에서 도는 CI는 병합 후 검증이며 결과를 확인해 실패하면 다음 작업으로 잡는다. 로컬 브랜치 삭제. 원격 브랜치는 저장소 자동 삭제 설정에 맡긴다.

## 7. 승인이 필요한 행동

CONSTITUTION.md 2-12항의 목록과 프로젝트 설정 E절. 승인이 필요한 단계 전까지 안전한 작업은 모두 마친 뒤 묻는다.

## 8. 새 프로젝트 적용

1. PROJECT_TEMPLATE.md를 복사해 채운다
2. 저장소 `docs/ai-dev-workflow/`에 CONSTITUTION·WORKFLOW 사본을 버전 헤더와 함께 둔다. CLAUDE.md 첫 줄은 "작업 전에 docs/ai-dev-workflow/CONSTITUTION.md와 WORKFLOW.md(vX.Y)를 읽고 따른다", 나머지는 B~H절의 프로젝트 값만. 규칙 문장은 복사하지 않는다
3. GitHub: main 보호(PR 필수, 승인 0명, 필수 체크, 강제 push·삭제 금지), head 브랜치 자동 삭제, 관리자 우회 적용, 공개 여부에 따른 가용성 확인
4. Claude Code: 권한 설정에서 main push·파괴적 명령 deny, 병합 명령 ask, 우회 옵션 deny
5. 독립 리뷰 도구 설치·인증, 자동 리뷰 게이트 끔
6. CI: `pull_request`와 main `push`에서 테스트·린트·빌드만. 경로 필터 없음. 필수 체크 이름을 보호 규칙과 일치시킨다
7. **세 수준 적용 확인** — 메인이 조회해 보고한다: 운영 원칙(사본과 CLAUDE.md), 도구 권한(새 세션에서 로드 확인), 서버 보호(`gh api`로 규칙 조회). 더해서 push·PR·병합으로 실행되는 워크플로 목록과 배포·외부 공개 연결 여부, 실행 검증의 데이터 분리 방식(새 브라우저 컨텍스트, 데스크톱 userData 임시 경로)을 확인한다. 셋이 다 있어야 하는 이유는 CONSTITUTION.md 5절
8. 첫 실제 작업으로 대표 플레이 경로 1~2개를 실행 검증 ①에 넣는다. 하네스가 없으면 그 확보가 첫 작업이다
9. 소규모 실제 작업으로 플로우를 검증한 뒤 본 작업 시작

공통 규칙이 개정되면 각 프로젝트의 사본 갱신은 별도 작업으로 하고, 위험도는 개정 내용의 실제 영향(검증·승인·권한 기준이 바뀌는지)으로 판단한다.

## 9. DECISIONS.md 구성

"제품 결정"은 사용자가 승인한 것만, 승인 표시와 함께. "기술 결정"은 AI에 위임된 것 중 나중에 참조할 것(아키텍처 선택, 거부한 대안, 이유). 미승인 제안은 어느 쪽에도 넣지 않는다.
