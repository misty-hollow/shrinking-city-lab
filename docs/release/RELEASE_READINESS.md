## 3. 성능 점검 (2026-09-25, 운영 빌드, 1920×1080, DPR 1)

측정은 `app/scripts/perf-probe.mjs`로 했습니다(headless Edge, 결과 `qa-shots/perf/perf.json`).
headless의 rAF는 이 PC 모니터(180 Hz)에 맞춰 돌기 때문에, fps 값은 **프레임 시간(ms)**으로 읽습니다.

| 조건 | 첫 조작 가능 | S0 회전 무대(계속 그림) | S4 조작 뒤 3초 | 위에서 보기 이동 | 긴 작업(최대) | 적응 화질 |
|---|---|---|---|---|---|---|
| 개발 PC GPU(RX 9070, D3D11) | 0.96초 | 5.6 ms/프레임(모니터 한계) | 20 ms 넘는 프레임 0% | 95% 5.6 ms | 425 ms(시작 때 세계 생성) | 그대로(DPR 1) |
| 같은 GPU + CPU 4배 느리게 | 2.7초 | 5.6 ms | 0% | 5.6 ms | 1.6초(시작 때) | 그대로 |
| 소프트웨어 GL(SwiftShader, 가장 약한 GPU 하한) | 2.1초 | 처음 6초 약 7 fps(145 ms) → 적응 뒤 약 10 fps(94 ms) | 1.1%(최대 100 ms) | 95% 100 ms | 1.7초(시작 때) | DPR 0.75 + 나무 절반 |
| 소프트웨어 GL + CPU 2배 | 1.7초 | 7 → 11 fps | 1.1% | 95% 106 ms | 1.2초 | DPR 0.75 + 나무 절반 |

공통 측정값:
- 내려받는 양: 1.5 MB
- JS 힙: 28~51 MB
- 콘솔 오류: 0
- 조작 → 결과 숫자 표시: 약 1.35초. 계산은 즉시 끝나고, 빛의 연출이 끝나야 숫자가 뜹니다(설계 의도)
- 이 PC에서 한 장면의 GPU 비용: 0.51 ms(드로우 39, 삼각형 약 50만). 개발 서버 브라우저 QA로 쟀습니다

**읽는 법과 병목**
- 첫 조작 5초 목표는 모든 조건에서 지켰습니다. 가장 느린 조건이 2.7초입니다.
- **가장 무거운 장면은 S0 회전 무대**입니다. 계속 그리는 유일한 화면이고, 플레이 중에는 바뀔 때만 그립니다.
- 소프트웨어 GL에서는 픽셀 비율을 낮춰도 좋아지지 않았습니다. **병목은 화소가 아니라 형상(삼각형 약 50만)**입니다. 나무를 줄였을 때 7→10 fps로 올랐습니다.
- 적응 화질 보완(이번 수정): 전에는 한 단계를 판단하려면 느린 프레임 90개를 모아야 했습니다. 그래서 10 fps 안팎에서는 한 단계에 10초 넘게 걸렸습니다. 이제 3초가 지나면(12프레임 이상) 판단합니다. 빠른 GPU의 동작은 그대로입니다.
- 시작 때 긴 작업(0.4~1.7초)은 세계 생성과 지형 굽기입니다. 첫 화면이 뜨기 전에 끝나므로 조작을 막지 않습니다. 플레이 중 긴 작업은 모든 조건에서 0입니다.
- 소프트웨어 GL은 실제 통합 GPU보다 훨씬 느린 하한입니다. **실제 통합 GPU 1080p 60fps 목표(설계안 6-12)는 아직 확인되지 않았습니다.**

**전시 기기에서 다시 잴 것**
- 방법: 전시 PC에서 `npm run build && npx vite preview --port 5198` → `PERF_PROFILES=gpu PERF_HEADED=1 node scripts/perf-probe.mjs`
- 기준: S0 프레임 가운데값 ≤ 16.7 ms, 20 ms 넘는 프레임 5% 이하, 첫 조작 5초 이하
- 미달이면 기록할 것: 적응 화질이 몇 단계까지 내려갔는지(`pixel_ratio.end`)와 GPU 이름(`renderer`)
- 시각 확인: 결과는 `qa-shots/perf/*-s4.png`로 눈으로 봅니다(나무가 줄어도 집·빛·탑은 그대로여야 합니다)
